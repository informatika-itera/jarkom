1. Prinsip & Arsitektur Lapisan Aplikasi

Paradigma Komputasi Terdistribusi, Kebutuhan Layanan Transpor (QoS), dan Pemetaan Port

Bagian pertama membahas prinsip dasar pengembangan aplikasi jaringan, perbandingan paradigma Client-Server vs P2P, serta pemetaan profil QoS ke protokol transpor.

Paradigma Aplikasi: Client–Server

Arsitektur Client–Server

Central Server (Always-On):

  • Host sentral yang selalu aktif melayani permintaan (24/7 always-on).
  • Memiliki IP Address publik statis permanen.
  • Ditempatkan di Data Center berskala besar demi skalabilitas & keandalan.

Clients (Heterogeneous End Systems):

  • Memulai kontak ke server secara on-demand (Request).
  • Dapat memiliki IP dinamis (DHCP/seluler) dan terputus sewaktu-waktu.
  • Klien tidak berkomunikasi langsung dengan klien lain.

Contoh Protokol: Web (HTTP/HTTPS), E-mail (SMTP/IMAP), FTP, DNS.

Gambar 12.1: Paradigma Arsitektur Komputasi Client–Server

Bandingkan skalabilitas arsitektur terpusat vs P2P. Pada Client-Server beban bertambah seiring jumlah klien, sedangkan pada P2P peer baru juga menyumbang kapasitas bandwidth untuk mengunggah file.

Paradigma Aplikasi: Peer to Peer (P2P)

Arsitektur Peer-to-Peer (P2P)

1. Karakteristik & Self-Scalability:

  • Tanpa Server Terpusat Permanen: End system (peer) berkomunikasi langsung satu sama lain.
  • Self-Scalability: Setiap peer baru yang meminta file (demand) otomatis menyumbang kapasitas komputasi & bandwidth unggah (service capacity).

2. Dua Tantangan Teknis Utama:

  • Proteksi NAT & Firewall (NAT Traversal): Pengguna rumahan/seluler berada di balik NAT (IP privat) dan firewall yang menolak koneksi masuk (inbound). Peer tidak bisa saling kontak langsung tanpa teknik hole punching (STUN/TURN/ICE).
  • Peer Churn (IP Dinamis & Offline): Node bebas keluar-masuk secara independen dan IP publik sering berganti → Menimbulkan beban sinkronisasi Distributed Hash Table (DHT) dan interupsi unduhan potongan file (chunks).
Contoh Implementasi: BitTorrent (distribusi file besar), Blockchain (Bitcoin, Ethereum).

Gambar 12.2: Paradigma Arsitektur Komputasi Peer-to-Peer (P2P)

Bandingkan skalabilitas arsitektur terpusat vs P2P. Pada Client-Server beban bertambah seiring jumlah klien, sedangkan pada P2P peer baru juga menyumbang kapasitas bandwidth untuk mengunggah file. Namun P2P menghadapi tantangan NAT traversal dan peer churn.

Kebutuhan Layanan Transpor bagi Aplikasi (QoS)

Setiap aplikasi mendefinisikan profil kualitas layanan (Quality of Service) ke lapisan transpor:

  • Integritas Data (Data Integrity):
    Aplikasi transfer file, finansial, dan email membutuhkan 100% loss-free (Reliable). Aplikasi multimedia dapat mentoleransi sedikit kehilangan paket (loss-tolerant).
  • Throughput: Bandwidth-Sensitive vs Elastic:
    • Bandwidth-Sensitive: Video streaming memerlukan ambang batas throughput minimum agar pemutaran tidak macet (buffer underrun). Trafik tidak harus konstan, melainkan bursty dan beradaptasi dinamis via DASH (1080p butuh ≈ 5 Mbps, 4K butuh ≈ 20 Mbps).
    • Elastic: Aplikasi web dan email dapat beroperasi pada bandwidth berapa pun (hanya durasi transfer yang berubah).
  • Sensitivitas Waktu (Timing / Latency):
    Game online dan panggilan suara (VoIP) memerlukan latensi sangat rendah (< 150 ms) agar interaktif tanpa jeda percakapan.
  • Keamanan (Security):
    Kerahasiaan data via enkripsi TLS/SSL, integritas pesan (anti-tampering), dan otentikasi identitas.
Profil kebutuhan layanan transpor aplikasi populer
Jelaskan bahwa lapisan aplikasi mendefinisikan apa yang dibutuhkan oleh proses pengguna, sedangkan lapisan transpor bertugas menyediakan layanan yang cocok sesuai kebutuhan tersebut. Tekankan bahwa multimedia modern bersifat adaptif (DASH).

Pemetaan Protokol Aplikasi ke Protokol Transpor

Aplikasi Protokol Aplikasi Protokol Transpor (Utama vs Alternatif)
File Transfer FTP (RFC 959) TCP Port 20, 21 (Reliable, bebas loss)
Web Browsing HTTP/1.1 & HTTP/2 TCP Port 80, 443
Electronic Mail SMTP, IMAP, POP3 TCP Port 25, 143, 110
DNS Resolution DNS (Port 53) Utama: UDP (1 RTT tanpa handshake)
Alternatif: TCP (Zone Transfer & balasan > 512 byte / DNSSEC)

Dasar Pemilihan Utama vs Alternatif: DNS mengutamakan UDP untuk kecepatan (fallback ke TCP jika flag Truncation TC=1 aktif). VoIP menolak retransmisi TCP karena paket suara yang datang terlambat 200 ms sudah basi dan tidak berguna.
Komparasi layanan: Reliable TCP vs Lightweight UDP
Ajak mahasiswa menghubungkan materi: TCP menjamin integritas data (loss-free), sedangkan UDP menjamin aktualitas waktu tanpa terhambat antrean retransmisi.

2. Protokol Web & Hypertext Transfer Protocol (HTTP)

Arsitektur Web, Sifat Stateless, Siklus RTT, Header HTTP, Cookies, Caching & Evolusi HTTP/2-3

Modul kedua membahas protokol pondasi web (HTTP), mekanisme pengalamatan URL, sifat stateless, siklus RTT, cookies, proxy cache, dan evolusi ke HTTP/2 dan HTTP/3.

Arsitektur Web & Sifat Stateless HTTP

Komponen Dokumen Web:

  • Halaman web tersusun atas Base HTML File dan beberapa Referenced Objects (gambar JPEG, video, CSS, JavaScript).
  • Setiap objek dialamatkan oleh sebuah URL (Uniform Resource Locator):
    http://www.itera.ac.id/jurusan/teknik-informatika/logo.png
    Host Name: www.itera.ac.id | Path: /jurusan/.../logo.png

Sifat Krusial HTTP: STATELESS

  • HTTP berjalan di atas TCP (Port 80 / Port 443 HTTPS).
  • Server melayani request klien, mengirimkan respon, lalu tidak mengingat apa pun tentang request klien di masa lalu.
  • Keuntungan: Desain server sangat sederhana, toleran terhadap kegagalan, dan memiliki skalabilitas tinggi.
Struktur URL dan relasi objek web
Jelaskan mengapa Tim Berners-Lee memilih sifat stateless untuk HTTP: server tidak perlu menyimpan status ribuan user secara kompleks, sehingga mampu melayani lonjakan trafik web.

Koneksi HTTP: Non-Persistent vs Persistent & RTT

1. Non-Persistent HTTP (HTTP/1.0):

  • Maksimal 1 objek dikirim melalui 1 koneksi TCP terbuka. Setelah objek terkirim, koneksi TCP langsung ditutup.
  • Jika halaman memiliki 1 base HTML + 10 gambar referensi, dibutuhkan 11 kali buka-tutup TCP!
  • Setiap objek memakan waktu: 2 × RTT + Transmit Time
    (1 RTT untuk 3-Way Handshake TCP + 1 RTT untuk Request/Response HTTP).

2. Persistent HTTP (HTTP/1.1):

  • Server membiarkan koneksi TCP tetap terbuka setelah mengirim respon.
  • Seluruh objek referensi berikutnya dikirimkan melalui koneksi TCP yang sama.
  • Objek referensi berikutnya hanya membutuhkan 1 × RTT! Menghemat beban kernel dan latensi pengguna secara masif.
Analisis RTT: 1st RTT (Handshake) + 2nd RTT (HTTP Request/Response)
Gambarkan RTT (Round Trip Time): waktu paket kecil bolak-balik dari klien ke server. Tekankan bahwa Non-persistent sangat boros karena mengulang handshake TCP untuk tiap gambar.

Anatomi Pesan HTTP Request

Format pesan HTTP berbasis teks ASCII yang terstruktur dalam 3 bagian:

GET /somedir/page.html HTTP/1.1  Request Line
Host: www.someschool.edu  Header Line
User-Agent: Mozilla/5.0 (Windows NT 10.0)
Accept: text/html,application/xhtml+xml
Accept-Language: id,en-US;q=0.7
Connection: keep-alive
 Baris Kosong Pemisah
[Entity Body Kosong pada Method GET]

Metode Request Populer:

  • GET : Meminta objek dari server (parameter di URL).
  • POST: Mengirim data formulir/payload dalam Entity Body.
  • HEAD: Meminta respon identik dengan GET tetapi tanpa entity body (untuk uji debugging/cache).
  • PUT / DELETE: Mengunggah file ke server / Menghapus file di server.
Struktur Request Line, Header Lines, dan Body
Jelaskan bahwa baris kosong ( ) adalah penanda mutlak bagi parser HTTP bahwa seluruh header telah selesai dibaca dan body data dimulai.

Anatomi Pesan HTTP Response & Status Codes

HTTP/1.1 200 OK  Status Line
Date: Sun, 15 Nov 2026 12:00:00 GMT
Server: Apache/2.4.41 (Ubuntu)
Last-Modified: Sat, 14 Nov 2026 08:30:00 GMT

<html><body><h1>Halo ITERA!</h1>... [Data Objek]

Katalog Kode Status Esensial:

Struktur Response: Status Line, Headers, dan Data Payload
Kategori status code: 2xx sukses, 3xx pengalihan/cache, 4xx kesalahan klien, dan 5xx kesalahan server internal.

Cookies: Membawa "State" pada Protokol Stateless

Bagaimana Tokopedia atau Shopee mengingat keranjang belanja kita jika HTTP itu pelupa (Stateless)? Jawabannya adalah Cookies.

Empat Komponen Mekanisme Cookie:

  1. Header Set-Cookie: ID=1634 pada HTTP response pertama dari server.
  2. Penyimpanan file cookie di perangkat klien (dikelola oleh browser).
  3. Header Cookie: ID=1634 pada seluruh HTTP request berikutnya ke situs tersebut.
  4. Basis data backend di server yang memetakan ID=1634 ke profil, riwayat, dan keranjang belanja pengguna.

Isu Privasi: Third-Party Tracking Cookies

  • Jaringan iklan (contoh: Google AdX) menaruh banner pada banyak situs berbeda.
  • Cookie pihak ketiga melacak rekam jejak browsing pengguna lintas situs web, menyusun profil preferensi pribadi tanpa disadari.
Alur 4 tahap transmisi cookie antara klien dan server
Jelaskan kompromi antara kenyamanan pengguna (login otomatis, keranjang belanja bertahan lama) versus privasi data (pelacakan perilaku belanja oleh third-party tracker).

Web Caches (Proxy Server) & Conditional GET

Tujuan Web Cache (Proxy Server):

  • Melayani permintaan klien tanpa melibatkan origin server.
  • Cache bertindak ganda: sebagai server bagi browser pengguna lokal, dan sebagai client bagi server asal di internet.
  • Ditempatkan di jaringan kampus/ISP untuk memangkas latensi respon dan menghemat konsumsi bandwidth tautan keluar.

Mekanisme Validasi: Conditional GET

  • Bagaimana memastikan file di cache belum usang (stale)?
  • Proxy mengirim request ke origin server dengan header:
    If-Modified-Since: <date_terakhir_di_cache>
  • Jika file belum berubah, origin server menjawab:
    HTTP/1.1 304 Not Modified (Body kosong / 0 byte data!).
  • Jika file berubah, server mengirim 200 OK beserta isi file baru.
Arsitektur Web Cache lokal di jaringan institusi
Conditional GET adalah inovasi cerdas: server hanya memberitahu bahwa file belum berubah tanpa perlu mentransmisikan ulang payload data berukuran megabyte.

Analisis Matematis: Evaluasi Kinerja Caching

Parameter Jaringan Kampus (Kurose & Ross):

• Ukuran Objek (L) = 100 kbit
• Link Akses ISP (R) = 1.54 Mbps
• Laju Kueri (r) = 15 req/detik
• RTT Internet Origin = 2.0 detik
1. Kondisi Tanpa Cache (Bottleneck Link Akses):
• Trafik Link = 15 req/s × 100 kbps = 1.50 Mbps
• Utilisasi Link Akses (I) = 1.50 Mbps / 1.54 Mbps ≈ 97% (Macet Total)
• Teori Antrean (M/M/1): Beban 97% menyebabkan penumpukan buffer → delay membengkak puluhan detik!
2. Solusi Pasang Web Cache LAN (Hit Rate h = 40%, Miss m = 60%):
• Delay Cache LAN ≈ 2 ms: Transmisi LAN 1 Gbps (≈ 0.1 ms) + baca memori RAM (≈ 1.9 ms) = 2 ms (0.002 s).
• Utilisasi Baru Link Akses: Ibaru = (0.60 × 1.50 Mbps) / 1.54 Mbps ≈ 58% (Antrean Lenyap).
Kalkulasi Rata-Rata Total Delay (Davg):
Davg = (h × DLAN) + (m × [DInternet + DLAN])
Davg = (0.40 × 0.002 s) + (0.60 × 2.002 s) ≈ 1.2 detik
Model matematis: Utilisasi link turun dari 97% ke 58%, delay terpangkas ke 1.2s
Buktikan bahwa dengan rumus ekspektasi matematis berbobot, penghematan dari cache lokal 2 ms dan penurunan utilisasi link langsung memangkas delay rata-rata menjadi 1.2 detik.

Evolusi Protokol Web: HTTP/1.1, HTTP/2, & HTTP/3

1. HTTP/1.1: Head-of-Line (HOL) Blocking di Lapisan Aplikasi

  • Objek dikirim secara serial (FIFO) dalam satu koneksi TCP. Jika objek pertama terhambat, seluruh objek berikutnya ikut tertahan antre.

2. HTTP/2 (2015): Binary Framing & Stream Multiplexing

  • Mengganti teks ASCII dengan frame biner.
  • Multiplexing: Banyak request/response dipecah menjadi frame-frame kecil berselang-seling (interleaving) dengan Stream ID di dalam satu koneksi TCP tunggal tanpa HOL blocking aplikasi. Browser langsung merender file kecil yang sudah selesai tanpa menunggu file besar.
  • Kelemahan (Transport HOL Blocking): Karena berjalan di atas satu pipa TCP tunggal, jika 1 paket TCP hilang di jaringan, seluruh buffer TCP membeku menunggu retransmisi → semua stream lain ikut macet!

3. HTTP/3 (2022): Migrasi ke QUIC (di atas UDP)

  • Menggantikan TCP dengan QUIC di atas UDP: Setiap stream memiliki nomor urut dan penanganan kehilangan paket secara mandiri.
  • Kehilangan paket pada 1 stream tidak membekukan stream lain! Terintegrasi TLS 1.3 bawaan dengan koneksi 0-RTT yang sangat cepat.
Evolusi: Dari transmisi sekuensial ke Stream Multiplexing & QUIC
Tekankan bagaimana revolusi web berpindah dari teks mentah ke frame biner, dan akhirnya melepaskan diri dari batasan kaku TCP dengan mengadopsi QUIC berbasis UDP.

3. File Transfer Protocol (FTP) & Ekosistem E-mail

Arsitektur Dual-Channel Out-of-Band FTP, SMTP Push, dan Komparasi Protokol Akses POP3 vs IMAP

Modul ketiga membedah protokol transfer berkas legendaris FTP dengan karakteristik dual-channel miliknya, serta arsitektur ekosistem email dari pengiriman (SMTP) hingga penarikan pesan (POP3/IMAP).

FTP: Arsitektur Dual-Channel Out-of-Band

Konsep Dasar FTP (RFC 959)

FTP (File Transfer Protocol) memisahkan dua saluran koneksi (Out-of-Band Control):

  • Control Connection (Port 21 TCP):
    Klien membuka koneksi kontrol ke server pada port 21 untuk mengirim perintah teks ASCII (USER, PASS, LIST, RETR, STOR) dan menerima status respon.
    Koneksi kontrol tetap terbuka sepanjang sesi pengguna aktif.
  • Data Connection (Port 20 / PASV TCP):
    Diciptakan secara terpisah murni untuk mentransmisikan berkas file riil.
    Dibuat baru & langsung ditutup otomatis untuk setiap 1 berkas!
Beda dengan HTTP: HTTP mengirimkan request baris, header kontrol, dan body data dalam satu saluran TCP yang sama (In-Band).

Gambar 12.8: Arsitektur Dual-Channel FTP (Port 21 Control & Port 20 Data)

Tekankan pembedaan Port 21 (Control/Perintah) dan Port 20 (Data/Transfer Berkas). Ini adalah konsep arsitektur klasik jaringan yang membedakan FTP dengan protokol modern.

Transmisi FTP: Active Mode vs Passive Mode (PASV)

Firewall, NAT, & Dilema Koneksi Masuk

Prinsip Stateful Firewall & NAT Klien:

  • Outbound (Keluar): Diizinkan bebas. Router NAT membuat tabel pemetaan port keluar otomatis.
  • Inbound (Masuk): DITOLAK secara default jika tidak diinisiasi dari dalam, untuk melindungi host dari peretas.

1. Active Mode (PORT) — Gagal Menembus Firewall & NAT:

  • Klien kirim perintah PORT N. Server Port 20 menginisiasi koneksi masuk (inbound) ke Port N klien.
  • Gagal: Firewall klien memblokir koneksi masuk asing, dan Router NAT tidak bisa me-routing paket ke IP privat klien!

2. Passive Mode (PASV) — Standar Internet Modern:

  • Server membuka port data acak P. Klien yang menginisiasi koneksi keluar (outbound) ke Server:P.
  • Sukses: Koneksi keluar diizinkan firewall klien dan ditranslasikan otomatis oleh router NAT.

Gambar 12.9: Komparasi Transmisi FTP Active Mode vs Passive Mode (PASV)

Jelaskan mengapa mahasiswa yang menggunakan FileZilla di jaringan kampus atau kosan sering gagal mentransfer file jika belum menyetel koneksi ke mode Passive (PASV).

Siklus Hidup Transmisi FTP: Multi-File Transfer

Alur 4 Fase Sesi FTP (RFC 959)

1. Setup Kontrol (Port 21 TCP — Persistent):

  • Klien inisiasi TCP ke Port 21 → Server sapa 220 Service Ready.
  • Autentikasi: USER / PASS → Server balas 230 Logged in.
  • Kanal kontrol tetap terbuka sepanjang sesi pengguna aktif.

2. Transfer Berkas 1 (Download file1.pdf):

  • Klien kirim PASV → Server buka Port data acak P1 (misal 49152).
  • Klien buka TCP ke Port P1 → kirim RETR file1.pdf di kontrol.
  • Data dialirkan via Port P1 → Selesai: Server kirim TCP FIN (Port P1 ditutup).

3. Transfer Berkas 2 (Upload file2.jpg):

  • Klien kirim PASV lagi → Server buka Port data baru P2 (misal 51200).
  • Klien kirim STOR file2.jpg → Data dialirkan via P2 → Selesai: Klien kirim TCP FIN (Port P2 ditutup).

4. Terminasi Sesi: Klien kirim QUIT → Server balas 221 Goodbye → Kanal Kontrol Port 21 ditutup.

Gambar 12.10: Siklus Hidup Transmisi FTP: Kontrol Persistent & Data Ephemeral per Berkas

Tekankan konsep penting: Kanal kontrol (Port 21) bersifat persistent (hidup dari awal sampai QUIT), sedangkan kanal data (Port PASV) bersifat ephemeral (dibuat baru dan langsung ditutup via TCP FIN untuk setiap satu berkas).

Ekosistem Surat Elektronik (E-mail)

Sistem email modern ditopang oleh 3 pilar komponen utama:

  • 1. User Agent (Mail Reader):
    Aplikasi antarmuka pengguna untuk menyusun, membaca, dan mengelola arsip email (contoh: Microsoft Outlook, Thunderbird, Apple Mail).
  • 2. Mail Server:
    Jantung infrastruktur pengiriman email. Memiliki dua struktur krusial:
    • User Mailbox: Gudang lokal untuk menyimpan seluruh pesan yang telah tiba bagi pengguna lokal.
    • Outgoing Message Queue: Antrean surat keluar yang menunggu giliran untuk dikirimkan ke mail server tujuan.
  • 3. Simple Mail Transfer Protocol (SMTP):
    Protokol standar antar-mail server untuk memindahkan surat melalui TCP Port 25 (atau Port 587 dengan enkripsi TLS).
Struktur Mailbox dan Outgoing Message Queue pada Mail Server
Ibaratkan Mail Server seperti kantor pos: memiliki kotak surat untuk setiap warga (Mailbox) dan kantong pengiriman untuk surat yang akan diberangkatkan (Queue).

Protokol SMTP: Alur Pengiriman Pesan

1. Dialog SMTP & Status Code (RFC 5321):

Kode Nama Status Arti & Alur Transaksi
220 Service Ready Server Greeting Banner: Server siap melayani setelah TCP terbentuk.
250 Action OK Perintah klien (HELO, MAIL FROM, RCPT TO) sukses diterima.
354 Start Mail Input Izin mengetik body email. Diakhiri tanda titik tunggal pada baris baru (.).
221 Closing Channel Respon penutupan koneksi setelah klien mengirim perintah QUIT.
Mengapa Server Berbicara Duluan (220 Greeting Banner)?
Secara transpor, klien memang yang menginisiasi TCP 3-way handshake. Namun pada layer aplikasi SMTP, klien wajib menunggu server menyapa terlebih dahulu untuk: (1) memastikan buffer antrean server siap, (2) mengumumkan kapabilitas ESMTP, dan (3) Early-Talker Defense (menangkal bot spam yang menembak perintah sebelum disapa).
Sekuens SMTP: Server Greeting (220) → Dialog Perintah → Closing (221)
Perlihatkan kesantunan dialog SMTP: klien menyapa dengan HELO, meminta izin pengirim, izin penerima, mengetikkan data, menutup dengan titik (.), lalu mengucapkan QUIT.

Protokol Akses Email: POP3 vs IMAP vs Webmail

POP3 (RFC 1939)

Port 110 / Port 995 (SSL)

  • Mode: Download and Delete (atau simpan lokal).
  • Surat diunduh ke satu komputer pengguna.
  • Client-Centric: Tidak ada sinkronisasi status (dibaca/belum) atau folder antar-perangkat berbeda.
  • Cocok jika kuota penyimpanan server sangat terbatas dan pengguna hanya memakai 1 PC.
IMAP (RFC 3501)

Port 143 / Port 993 (SSL)

  • Mode: Server-Centric Sync.
  • Seluruh pesan dan struktur folder (Sent, Draft, Trash) tetap disimpan di server.
  • Status pesan (dibaca, dibintangi, dihapus) langsung tersinkronisasi otomatis di laptop, smartphone, dan tablet.
  • Standar de-facto aplikasi email modern (Outlook, Apple Mail).
Webmail (HTTP/HTTPS)

Port 80 / Port 443 (HTTPS)

  • Pengguna mengakses mailbox melalui peramban web (Gmail, Outlook Web).
  • Klien ↔ Mail Server menggunakan protokol HTTP/HTTPS.
  • Antar-Mail Server tetap berkomunikasi menggunakan protokol SMTP.
  • Sangat praktis tanpa perlu instalasi aplikasi klien khusus.
Mengapa Butuh Protokol Akses? SMTP adalah protokol Push (mengirimkan surat ke kotak pos tujuan). Bob tidak bisa menggunakan SMTP untuk menarik (pull) surat miliknya dari mailbox server!
Tekankan perbedaan konsep: SMTP adalah protokol dorong (push), sedangkan POP3, IMAP, dan HTTP adalah protokol tarik (pull). Jelaskan keunggulan IMAP dalam sinkronisasi multi-device.

4. Domain Name System (DNS) & Keamanan Resolusi

Arsitektur Basis Data Terdistribusi, Resolusi Iterated vs Recursive, Resource Records & DNSSEC

Modul keempat membedah sistem penamaan domain internet (DNS): alasan desentralisasi, hierarki 4 tingkat, penelusuran iterated vs recursive, struktur record, dan keamanan DNS.

DNS: Layanan & Alasan Desentralisasi

Layanan Utama DNS:

  • Translasi Hostname ke IP: Manusia mudah mengingat nama (www.itera.ac.id), namun router jaringan mutlak memerlukan alamat IP biner (103.111.201.21).
  • Host Aliasing: Domain alias kanonikal yang mudah dibaca.
  • Mail Server Aliasing: Memetakan nama server email institusi (MX Record).
  • Load Distribution: Memetakan satu domain populer ke sekumpulan alamat IP server replika secara round-robin.

Mengapa DNS Tidak Boleh Disentralisasi (1 Server Dunia)?

  • Single Point of Failure (SPOF): Jika satu server pusat tersebut meledak/down, seluruh internet dunia mati total!
  • Volume Trafik: Milyaran perangkat menembakkan query bersamaan.
  • Jarak Jaringan: Latensi tinggi bagi pengguna yang jauh dari lokasi server.
  • Pemeliharaan Raksasa: Database raksasa mustahil dikelola satu entitas.
Translasi nama domain ke alamat IP numerik
DNS adalah basis data terdistribusi terbesar dan paling tangguh di muka bumi, dirancang dengan sistem hierarkis agar tidak ada satu titik kegagalan tunggal.

Hirarki Global Server DNS

Mekanisme pencarian DNS bekerja secara berjenjang dari atas ke bawah:

  1. Root DNS Servers (13 Gugus Logika A s.d. M):
    • Arti Gugus A s.d. M: Nama resmi 13 server root internet (a.root-servers.net s.d. m.root-servers.net) yang dikelola 12 lembaga independen (Verisign, NASA, ICANN, WIDE, dll.).
    • Mengapa Tepat 13? Batasan historis paket DNS via UDP maksimal 512 bytes (RFC 1035) yang hanya muat data 13 server root.
    • Bukan 13 Komputer Fisik: Menggunakan teknologi IP Anycast, di mana tiap gugus direplikasi ke ratusan server fisik di seluruh dunia (> 1.700 server fisik global).
  2. Top-Level Domain (TLD) Servers:
    Mengelola domain tingkat teratas: Generic TLD (.com, .org, .edu) dan Country-Code TLD (.id, .uk, .jp).
  3. Authoritative DNS Servers:
    Server resmi milik organisasi yang menyimpan catatan asli host (misal DNS resmi kampus).
  4. Local DNS Resolver:
    Server DNS milik ISP/kampus yang menerima kueri awal dari host pengguna dan melakukan penelusuran berjenjang.
Pohon hierarki: 13 Root Anycast → TLD → Authoritative
Perjelas bahwa laptop mahasiswa tidak langsung mengontak Root Server, melainkan menitipkan kueri ke Local DNS Server (Resolver ISP/Kampus).

Metode Resolusi DNS: Iterated

Iterated Query ("Tanya Server Rujukan")
  1. Host meminta translasi ke Local DNS Resolver.
  2. Local DNS bertanya ke Root DNS. Root merujuk: "Silakan tanya ke TLD .edu".
  3. Local DNS bertanya ke TLD .edu. TLD merujuk: "Silakan tanya ke Authoritative example.edu".
  4. Local DNS bertanya ke Authoritative example.edu → Mendapatkan IP target asli!

Mengapa Root Tidak Terbebani? Root Server bersifat Stateless: hanya memberi alamat rujukan server TLD lalu langsung lepas tangan (menutup sesi). Beban komputasi dan antrean menunggu dibebankan ke Local DNS Resolver.

Gambar 12.12: Alur Kueri DNS Iterated (Standar Global)

Tekankan mengapa Internet memilih kueri Iterated pada tingkatan atas: jika Root dipaksa melakukan recursive, Root Server akan tumbang dalam hitungan detik karena kelelahan memori antrean.

Metode Resolusi DNS: Recursive

Recursive Query ("Terima Beres")
  1. Host meminta Local DNS mencari sampai dapat.
  2. Local DNS melempar query berantai ke Root Server.
  3. Root Server yang repot bertanya ke TLD.
  4. TLD yang repot bertanya ke Authoritative, lalu jawaban dikembalikan berantai ke bawah.

⚠️ Beban Komputasi Berat: Ditolak di Internet publik karena membebani antrean memori server akar (Root).

Gambar 12.12: Alur Kueri DNS Recursive (Rantai Beban di Akar)

Recursive query hanya digunakan antara Klien dan Local DNS Resolver. Antara Local DNS ke Root/TLD mutlak menggunakan Iterated.

Format Resource Record (RR) & Caching DNS

Database DNS menyimpan data dalam format tuple 4 nilai:

(Name, Value, Type, TTL)

Tipe Name Value Keterangan Fungsi
Type A Hostname Alamat IPv4 Translasi standar nama host ke IPv4 (example.com → 103.111.201.21).
Type AAAA Hostname Alamat IPv6 Translasi ke format 128-bit IPv6.
Type NS Domain Host Name Server Menunjuk Authoritative Name Server domain (dns1.example.com).
Type CNAME Nama Alias Nama Kanonikal Alias ke nama asli server (relay1.example.com → example.com).
Type MX Domain Host Mail Server Menentukan server penampung email masuk domain (mail.example.com).
DNS Caching & TTL: Penyelamat Beban Server Root!
Begitu Local DNS menerima jawaban rujukan TLD/Authoritative, ia menyimpannya di memori RAM selama durasi TTL (biasanya 48 jam / 2 hari). Akibatnya, jutaan kueri pengguna berikutnya langsung dijawab dari cache lokal → lebih dari 99% kueri DNS di dunia tidak pernah menyentuh Root Server lagi!
Struktur database Resource Record (RR) DNS
Jelaskan bahwa TTL yang panjang melindungi Root Server dari beban berlebih. Saat institusi mengganti IP server web, propagasi perubahan membutuhkan waktu hingga masa TTL pada cache DNS seluruh dunia habis.

Keamanan DNS: Ancaman Serangan & Solusi DNSSEC

Sebagai infrastruktur terpenting internet, DNS sering menjadi target serangan:

  • 1. Serangan DDoS (Distributed Denial-of-Service):
    Membombardir Root Servers dengan trafik sampah agar layanan lumpuh.
    Pertahanan: Sangat tangguh berkat teknologi Anycast routing dan perlindungan caching berlapis di Local DNS seluruh dunia.
  • 2. DNS Cache Poisoning / DNS Spoofing:
    Penyerang mengirim balasan palsu ke Local DNS resolver sebelum jawaban asli tiba. Akibatnya resolver menyimpan IP palsu (korban yang membuka web bank dibelokkan ke web phishing hacker).
  • 3. Solusi Industri: DNSSEC (DNS Security Extensions):
    Menyediakan otentikasi asal data dan integritas pesan menggunakan kriptografi kunci publik. Setiap Resource Record ditandatangani secara digital (RRSIG). Resolver dapat memvalidasi apakah data DNS benar-benar berasal dari pemilik domain yang sah.
Ancaman eksploitasi DNS Spoofing & pertahanan DNSSEC
Soroti bahwa protokol DNS standar pada awalnya dirancang tanpa enkripsi/tanda tangan, sehingga inovasi DNSSEC sangat vital untuk mencegah pembajakan domain internet.

Eksplorasi Praktis:

CLI Tools (cURL & DNS)

1. Inspeksi Header HTTP via cURL

Mengambil Header Saja (Tanpa Body Payload):

$ curl -I https://www.example.com
HTTP/2 200
server: nginx
strict-transport-security: max-age=31536000
  • -I: Parameter HEAD request (hanya minta metadata header, hemat bandwidth).
  • 200 OK: Dokumen ditemukan & valid. HSTS: Wajib HTTPS 1 tahun.

Uji Conditional GET (Verifikasi Cache):

$ curl -I -H "If-Modified-Since: Sun, 15 Nov 2026 14:00:00 GMT" https://www.example.com
HTTP/2 304 Not Modified
  • -H: Parameter kirim header kustom.
  • 304 Not Modified: File belum diedit, browser pakai cache lokal.
2. Eksplorasi DNS via nslookup & dig

Pencarian Mail Exchanger (MX Record):

$ nslookup -type=MX example.com
example.com mail exchanger = 1 mail.example.com.
  • -type=MX: Parameter kueri spesifik server mail. Nilai 1 adalah tingkat prioritas (tertinggi).

Pelacakan Hirarkis Delegasi DNS (+trace):

$ dig +trace www.example.com
.           518400 IN NS a.root-servers.net.
id.         172800 IN NS a.dns.id.
example.com. 86400  IN NS dns1.example.com.
www.example.com. 3600 IN A 103.111.201.21
  • +trace: Mematikan kueri rekursif resolver dan melacak berjenjang dari Root (.) → TLD (.id) → Authoritative → IP host final. Angka: sisa durasi TTL (detik).
Ajak mahasiswa mempraktikkan langsung: curl -I dan dig +trace adalah dua senjata diagnosis utama network engineer untuk mendeteksi masalah web dan DNS.
